よくある誤解

世の中には「あの有名な俳優の公式サイトは情報量がたくさん載っているのに表示が速い。だから情報量が多いこと自体がすごいのだ」と勘違いしている人が大量にいます。 これは因果関係を取り違えています。速さの理由は情報量の多さではなく、情報の載せ方にあります。

ページの表示速度を決めるのは、主に転送するバイト数とリクエストの数です。日本語のテキストは1文字あたり数バイトで、長文を10万字並べてもせいぜい数百キロバイトです。 一方、写真を1枚追加すれば数百キロバイトから数メガバイト、広告タグや解析スクリプトを1つ追加すれば数十から数百キロバイトが簡単に乗ります。 つまりテキストは驚くほど軽く、画像・動画・スクリプトは驚くほど重いのです。

結論：長文が速いのではなく、長文でも画像やJavaScriptを載せていなければ速い。情報量は速度の敵ではありません。

なぜテキストベースのページは速いのか

代表的な「速いサイト」とされる古典的な個人サイトの構造を思い出すと、その理由はすぐに分かります。共通しているのは次のような要素です。

  • HTML が素朴で、要素の入れ子が浅い。
  • CSS が小さく、外部フォントを読み込んでいない。
  • JavaScript をほぼ、あるいはまったく使っていない。
  • 画像が極端に少ない。あってもアイコン程度。
  • 広告、アクセス解析、SNS埋め込み、タグマネージャが無い。
  • 1ページが1リクエストで完結し、追加の取りこぼしが無い。
  • 古い端末でも動く、無駄の無いマークアップ。

これらはすべて「情報量」ではなく「実装の重さ」の話です。同じ内容量でも、画像を大量に貼り、外部フォントを読み、スクリプトを何本も走らせれば、あっという間に遅くなります。 逆に、どれだけ文章が長くても、上の条件を守っていれば驚くほど速いままです。

転送量の目安

おおよその感覚として、次を覚えておくと見積もりが楽になります。数値は用途や圧縮設定で変わりますが、桁の感覚はおおむねこの通りです。

要素おおよその重さ速度への影響
日本語のテキスト1万字約20〜40KB（gzip後は更に小さい）ごく小さい
CSS 1ファイル数KB〜数十KB小さい
JavaScript ライブラリ1本数十KB〜数百KB大きい
写真1枚（フルHD相当）300KB〜2MB非常に大きい
Webフォント1書体50KB〜数MB大きい（FOIT/FOUTの原因）
動画の自動再生数MB〜致命的
広告・解析タグ数十KB〜数百KB＋追加リクエスト大きい

表を見れば明らかです。文章をいくら増やしても、画像やスクリプト1本にはかないません。だから「長文なのに速い」は技術的にはむしろ自然なことなのです。

GitHub Pages の強み

では、その軽いテキストページをどこに置くと快適に配信できるのか。選択肢のひとつが GitHub Pages です。静的ファイルをそのまま置くだけで、次のような恩恵を自動的に受けられます。

  • CDN配信：世界中のエッジから近い場所で応答するため、初回接続が速い。
  • HTTP/2 以上：多重化により、複数ファイルの取得が効率的。
  • 圧縮：テキストは自動的にgzipやBrotliで圧縮して転送される。
  • キャッシュ制御：適切なヘッダが付き、2回目以降はさらに速い。
  • 無料・HTTPS既定：証明書の管理が要らず、常時TLSで配信される。
  • ビルド不要：HTML/CSS/JSをそのままpushするだけで公開できる。

ここでも重要なのは「軽いものを置けば、配信基盤がさらに後押ししてくれる」という関係です。基盤がどんなに良くても、数メガバイトのデータを毎回送れば遅くなります。 逆に、テキスト中心の軽いページなら、GitHub Pages のCDNと圧縮が効いて、体感はほぼ一瞬になります。

速さは「置き場所」と「置くもの」の掛け算です。GitHub Pages は置き場所の点で非常に優秀ですが、置くものが重ければ意味がありません。

実測の考え方

「体感で速い」だけでなく、数字で確かめると誤解が解けます。最低限、次の指標を見ておけば十分です。

  1. 転送バイト数：そのページが合計で何KBを運んでいるか。
  2. リクエスト数：何個のファイルを取りに行っているか。
  3. TTFB（最初の1バイトまでの時間）：サーバと回線の応答の速さ。
  4. LCP（最大コンテンツの描画）：主要な内容が表示されるまで。
  5. CLS（レイアウトのずれ）：読み込み中のガタつき。

ブラウザの開発者ツールのネットワークタブを開き、再読み込みして合計サイズと件数を見るだけでも、原因の大半は特定できます。 「情報量が多いのに速い」と思っていたページの合計サイズが、実は数十KBしかないことに驚くはずです。

よくある勘違いの正体

誤った見方実際
長文だから速い長文は軽い。むしろ情報を増やすほど中身が濃くなる。
デザインが古いから速いデザインの新旧は速度と無関係。重い装飾が無いことが本質。
フレームワークを使わないと遅い逆。素朴なHTMLは最速の部類。フレームワークは往々にして重い。
画像が多い方がリッチで速い画像は最も重い要素。リッチさと速度はトレードオフ。
キャッシュだけが速さの理由初回表示の軽さも本質。初回が軽いからキャッシュも効く。

軽くする手順

情報量を保ったまま速くしたいときは、次の順番で手を入れると効果的です。上から順に効きが大きいので、全部を一度にやる必要はありません。

  1. 広告・解析・埋め込みを棚卸しし、無くせるものを消す。
  2. 画像を減らす、縮める、遅延読み込みにする。
  3. Webフォントをやめ、端末内蔵フォントに戻す。
  4. JavaScript の本数とサイズを減らす。不要な機能は削る。
  5. CSS を1ファイルにまとめ、未使用ルールを削る。
  6. HTML を素朴に保ち、要素の入れ子を浅くする。
  7. 静的ファイルとして配信し、サーバ側の処理を無くす。

ここまで読むと分かる通り、努力の方向は「情報を減らす」ではなく「重いものを減らす」です。文章はどんどん足しても構いません。 情報量を保ったまま速いページを作ることは、十分に可能で、しかも簡単です。

よくある質問

Q. 情報量が多いほど遅くなるのでは？

A. テキストの量がそのまま遅さになるわけではありません。テキストは軽く、圧縮もよく効きます。遅さの主因は画像・動画・スクリプト・外部タグです。

Q. 古い作り方の方が速いのはなぜ？

A. 古いから速いのではなく、軽いから速いのです。同じ軽さなら新しい技術でも速くできます。技術の新旧と速度は別の軸です。

Q. GitHub Pages なら必ず速い？

A. 配信基盤は優秀ですが、置くファイルが重ければ遅くなります。軽いファイルと組み合わせて初めて最大の効果が出ます。

Q. フレームワークを使うと遅くなる？

A. 使い方次第ですが、素朴な静的HTMLに比べれば一般に重くなります。文章主体のページなら、最初から素朴に作るのが最も速い選択です。

Q. 結局いちばん大事なことは？

A. 「情報量」ではなく「重いリソース」を減らすこと。文章は好きなだけ書いてよい、という一点です。
